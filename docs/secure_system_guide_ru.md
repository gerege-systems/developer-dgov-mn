## 0. Моделирование угроз

**Цель:** архитекторы совместно договариваются и записывают, «от чего защищаемся»
и «кто и что хочет получить». Без этого анализа любая работа по безопасности идёт вслепую.

### 0.1 Модели, которые стоит сочетать

| Модель | Для чего | Как |
|---|---|---|
| **STRIDE** | Microsoft. Угрозы на уровне компонентов | Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege |
| **DREAD** | Для оценки | Damage, Reproducibility, Exploitability, Affected users, Discoverability (каждое 1–10) — сортировка по сумме |
| **PASTA** | 7 этапов от бизнес-риска | Для каждой угрозы сопоставить бизнес-контекст и ущерб |
| **LINDDUN** | Угрозы приватности | Linkability, Identifiability, Non-repudiation, Detectability, Disclosure of information, Unawareness, Non-compliance |
| **MITRE ATT&CK** | Отображение реального поведения атакующих | По TTP (тактики/техники/процедуры) пишутся правила обнаружения |

### 0.2 Процесс

1. Нарисуйте **диаграмму потоков данных (DFD)** — отметьте границы доверия (DMZ, внутренняя сеть, БД).
2. Пройдитесь по STRIDE на каждой границе.
3. Пройдитесь по LINDDUN на потоках с PII.
4. Оцените риски по DREAD и устраните первые 10.
5. **Модель угроз = код** — храните `THREAT_MODEL.md` в репозитории. На каждом
   ревью PR спрашивайте: «появляется ли здесь новая граница доверия?»

**Инструменты:** Microsoft Threat Modeling Tool (бесплатно), OWASP Threat Dragon
(открытый), IriusRisk (корпоративный).

## 1. Аутентификация

**NIST SP 800-63B Digital Identity Guidelines** — мировой стандарт.
В нём три уровня AAL (Authenticator Assurance Level):

| Уровень | Значение | Пример применения |
|---|---|---|
| **AAL1** | Один фактор (пароль) | Публичная рассылка, потребительское приложение с низким риском |
| **AAL2** | Обязательна многофакторность, устойчивость к повтору | Практически любая SaaS и бизнес-приложение |
| **AAL3** | На аппаратной основе (FIDO2 / смарт-карта), устойчивость к подмене проверяющего | Госсектор, банки, админ здравоохранения |

> **Цель по умолчанию для нашего шаблона: AAL2.** У основных пользователей должна
> быть MFA; роль администратора должна быть готова к переходу на AAL3.

### 1.1 Пароли — современные правила (NIST 800-63B §5.1.1)

**Правильно:**

- **Ставка на длину** — минимум 8, рекомендуется 12+. **Правила сложности**
  (буквы, цифры, символы) официально признаны NIST вредными с 2017 года
  (пользователи обходят их шаблонами).
- Блокируйте утёкшие пароли через **Have I Been Pwned API**. Формат префикса с
  k-анонимностью — `https://api.pwnedpasswords.com/range/<sha1[0:5]>`
  (полный хеш на сервер не уходит).
- **Никогда не требуйте плановой смены** (раньше говорили «каждые 60 дней») —
  меняйте только при утечке или признаках атаки.
- Хеш: **`argon2id`** (memory=64MB, t=3, p=2), готовый рецепт —
  `golang.org/x/crypto/argon2`. Либо `bcrypt` с cost ≥ 12.
  **Оба варианта — стандарт по OWASP.**

```go
import "golang.org/x/crypto/argon2"

// Минимум, рекомендованный OWASP (2024)
hash := argon2.IDKey([]byte(password), salt, 3, 64*1024, 2, 32)
```

**Никогда:**

- MD5 или SHA-256 напрямую для паролей (почти ничего не выдержит — быстрый хеш = дешёвый перебор)
- Хранение в открытом виде или обратимым шифрованием
- Собственное изобретение схемы «соль + хеш»
- Секретные вопросы вроде «девичья фамилия матери» — это публичные данные, находятся через OSINT

### 1.2 Аутентификаторы — иерархия

**Чем выше, тем лучше:**

1. **Passkeys / WebAuthn (FIDO2)** ⭐ — устойчивы к фишингу, соответствуют NIST
   AAL3, без паролей. iOS 16+, Android 9+, все крупные браузеры.
   **Любой новый проект должен поддерживать passkey с самого начала.**
2. **Аппаратный ключ безопасности (YubiKey)** — для администраторов.
3. **TOTP** (Google Authenticator, Authy) — надёжно, работает офлайн. `github.com/pquerna/otp/totp`.
4. **Push-уведомление** (внутри собственного мобильного приложения) — хороший UX и
   сильное подтверждение канала аутентификации.
5. **Magic link по почте** — допустим как дополнительный фактор. В серьёзном
   приложении не должен быть основным фактором (взлом почты рушит всё).
6. **SMS OTP** — **устарело** (NIST 800-63B с 2017 года относит к «RESTRICTED»).
   Подмена SIM, атаки SS7. Только как запасной вариант для унаследованных пользователей.

### 1.3 Стратегия сессий

| Модель | Web | Мобильные | Отзыв | Устойчивость к фишингу |
|---|---|---|---|---|
| **Серверная сессия** (кука + Postgres/Redis) | ⭐ Идеально | ОК | Просто | Кука + CSRF-токен |
| **JWT (stateless)** | ОК | ОК | Сложно (чёрный список) | Ниже (токен можно злоупотребить) |
| **PASETO / Biscuit** | ОК | ОК | Сложно | Лучше JWT |
| **OAuth2 + OIDC** | ⭐ Корпоративно | ⭐ Корпоративно | Интроспекция токена | Наивысшая |

**Рекомендация:** **для web — серверная сессия**
(`SameSite=Lax + Secure + HttpOnly`), **для мобильных — OAuth2 с ротацией
refresh-токена**, **для корпоративных сценариев — OIDC** (Keycloak, Auth0,
Ory Hydra). Не выбирайте JWT «потому что дешевле» — сложность отзыва порождает
проблемы соответствия.

### 1.4 Ротация refresh-токена (детали)

Эталонный шаблон:

1. Пользователь входит → `access_token` (15 мин) + `refresh_token_v1`
   (30 дней, генерируется случайно, в базе хранится хеш).
2. Мобильный/веб-клиент обменивает `refresh_token_v1` на новый токен → сервер
   отзывает `refresh_token_v1` и выдаёт `refresh_token_v2`.
3. **Если `refresh_token_v1` приходит снова — отзывается всё семейство токенов**
   (обнаружение повторного использования). Пользователь входит заново.
   Описано в RFC 6819 §5.2.2.3.

```go
// Набросок — всему семейству токенов даётся общий "session_id".
// При обнаружении повтора отзываются все refresh этого session_id.
```

### 1.5 Блокировка аккаунта, лимиты, перечисление аккаунтов

- **Лимит запросов:** endpoint входа — 5 запросов/мин/IP. Проверка bcrypt стоит
  считаные миллисекунды, поэтому нужен ещё счётчик по пользователю (Redis).
- **Блокировка:** 10 неудач → мягкая блокировка на 15 минут. Для обнаружения
  распределённого перебора счётчик по пользователю важнее счётчика по IP.
- **Избегайте перечисления аккаунтов:**
  - Не различайте «почта не найдена» и «пароль неверный» → одно сообщение:
    «неверная почта или пароль».
  - Endpoint восстановления пароля: независимо от существования аккаунта
    отвечайте «если эта почта зарегистрирована, ссылка отправлена» — это скрывает
    факт существования учётной записи.
  - Регистрация: не выдавайте «эта почта уже используется» напрямую; сообщайте
    через письмо подтверждения.

### 1.6 Потоки восстановления

> **Важный вывод исследований:** более 40% захватов аккаунтов происходит через
> потоки восстановления. Один раз перехваченное письмо восстановления — и всё потеряно.

- Коды восстановления (10 штук) — храните в виде хеша. Сохраняйте только после
  того, как пользователь подтвердил, что записал их.
- Восстановление пароля идёт через одноразовый OTP-код (GeregeCloud Verify):
  у кода короткий TTL (около 30 мин), он одноразовый, и код никогда не пишется в
  серверные логи. Сброс имеет форму `{email, code, new_password}` — а не ссылки/токена сброса.
- Восстановление по почте или телефону само по себе — это AAL1; при сбросе
  пароля пользователю уровня AAL2 обязательно добавляйте дополнительную проверку.

### 1.7 OAuth2 / OIDC

- Параметр `state` обязателен (защита от CSRF).
- **PKCE обязателен**, даже для конфиденциальных клиентов (с 2024 года требуется BCP RFC 9700).
- `redirect_uri` — строгий белый список с точным совпадением.
- Не храните токены в localStorage; используйте HttpOnly-куки.
- Доверяйте claims в ID-token только после проверки подписи. Остерегайтесь
  `alg: none` и атак на подмену ключа.

### 1.8 Соответствие стандартам

| Стандарт | Соответствующие пункты |
|---|---|
| OWASP ASVS v4 | V2 Authentication, V3 Session |
| NIST SP 800-63B | Все требования AAL |
| OWASP Cheat Sheet | Authentication, Password Storage, Session Management |
| RFC 6749 / 6750 / 8252 / 9700 | OAuth2 (BCP для мобильных нативных приложений) |
| WebAuthn L3 | Вход без пароля |

## 2. Авторизация

> Аутентификация = «кто ты?»  Авторизация = «что тебе можно?»

### 2.1 Модели

| Модель | Детализация | Производительность | Пример |
|---|---|---|---|
| **RBAC** (по ролям) | Грубая | Быстро, мало JOIN | "admin", "support" — в этом шаблоне |
| **ABAC** (по атрибутам) | Средняя | Средняя | «Видеть только файлы своего арендатора» |
| **ReBAC** (по связям) | Точная | Нужен граф в БД | Google Drive — «поделились с вами» → SpiceDB, OpenFGA |
| **Policy-as-Code** | Возможно всё | Нужен кэш | Open Policy Agent (Rego), AWS Cedar |

**Рекомендация для шаблона:** RBAC + ABAC (изоляция арендаторов), для
корпоративных сценариев добавьте ReBAC + OPA.

### 2.2 IDOR (OWASP A01:2021 Broken Access Control)

Самая повторяющаяся уязвимость. Сервер обязан проверять **принадлежность** для
каждого ресурса:

```go
// НЕВЕРНО — IDOR
func GetInvoice(invoiceID string) (*Invoice, error) {
    return db.Get(invoiceID)
}

// ВЕРНО — двойная проверка арендатора и владельца
func GetInvoice(ctx context.Context, invoiceID string) (*Invoice, error) {
    inv, err := db.Get(ctx, invoiceID)
    if err != nil { return nil, err }
    if inv.TenantID != tenant.ID(ctx) { return nil, ErrNotFound } // NotFound, а не Forbidden
    if !canAccess(ctx, inv) { return nil, ErrForbidden }
    return inv, nil
}
```

Кроме того, **используйте UUID, а не последовательные целочисленные ID**.
Последовательные ID легко перебираются (1, 2, 3, …).

### 2.3 BOLA / BFLA (OWASP API Top 10)

- **BOLA** (Broken Object Level Authorization) — A1:2023. Пример:
  `GET /api/v1/users/1234/notes` — а если 1234 — чужой ID?
- **BFLA** (Broken Function Level Authorization) — A5:2023. Пример:
  `POST /admin/users` — точка входа не защищена на уровне HTTP, и обычный
  пользователь получает доступ.

Надёжнее всего описывать проверки разрешений для всех endpoint на слое ABAC.

### 2.4 Изоляция арендаторов (шаблон этого проекта)

В пакете `internal/tenant`:

```go
// Все запросы репозитория автоматически получают WHERE tenant_id=? через tenant.Scope(ctx)
db.WithContext(ctx).Scopes(tenant.Scope(ctx)).Find(&items)
```

**Эшелонированно:**

1. **Слой приложения** — middleware кладёт tenant_id в ctx + Scope в репозитории.
2. **Слой БД** — RLS в Postgres (раздел 3.3 ниже). Одного приложения мало; при
   ошибке база сама остановит утечку.
3. **Слой тестов** — автотест проверяет, что «пользователь A при обращении к
   данным арендатора B получает 404». Ручное тестирование здесь не спасает.

### 2.5 Пример Cedar / OPA (продвинутое)

Если матрица разрешений становится слишком сложной (например, шеринг файлов) —
переходите к policy-as-code:

```rego
# OPA Rego — «можно смотреть файл, которым с тобой поделились»
package files.access
default allow = false
allow {
  input.user.tenant_id == input.file.tenant_id
  input.user.id == input.file.owner_id
}
allow {
  some share
  share := data.shares[_]
  share.file_id == input.file.id
  share.shared_with == input.user.id
  share.expires_at > time.now_ns() / 1000000000
}
```

## 3. Безопасность PostgreSQL

### 3.1 SQL-инъекции (OWASP A03:2021)

**Параметризованные запросы — обязательно. Без исключений.**

```go
// ✅ pgx, database/sql — через плейсхолдеры
db.QueryRow(ctx, "SELECT id FROM users WHERE email = $1", email)

// ❌ НИКОГДА
db.Query(ctx, fmt.Sprintf("SELECT * FROM users WHERE email='%s'", email))
```

**Инструменты:**

- `sqlc` — проверяет SQL на этапе компиляции, типобезопасно.
- `gosec` — SAST для Go, находит шаблоны SQL-инъекций.
- pg_query_go — предварительная валидация через разбор запроса.

**Пользовательский ввод в ORDER BY/LIMIT:** белый список имён колонок
(сравнение только с разрешёнными строками), остальное отклонять.

### 3.2 Атака на search_path (CVE-2018-1058)

Если атакующий может влиять на конфигурацию `search_path` в PostgreSQL, он
способен подложить троянскую функцию в схему `public` и перехватить вызовы части функций.

```sql
-- При работе приложения обязательно:
ALTER ROLE app_user SET search_path = "$user", app_schema, public;
-- либо в строке подключения options="-c search_path=app_schema"
```

### 3.3 Row-Level Security (RLS) — по tenant_id

Колонки tenant_id в этом шаблоне защищены на слое приложения.
**Эшелонированно добавьте вторую защиту на слое БД:**

```sql
ALTER TABLE notifications ENABLE ROW LEVEL SECURITY;
ALTER TABLE notifications FORCE ROW LEVEL SECURITY; -- действует и на владельца таблицы

CREATE POLICY tenant_isolation ON notifications
  FOR ALL
  USING (tenant_id = current_setting('app.tenant_id')::int);

-- В каждом подключении приложения:
-- SET app.tenant_id = '42'; — из middleware
```

Если из-за ошибки приложение выполнит запрос без tenant_id, база сама разделит
данные и остановит утечку.

**Для админских и межарендных запросов** используйте отдельную роль БД с правом
`BYPASSRLS`. Обычный `app_user` обходить RLS не должен.

### 3.4 Разделение пользователей БД

```sql
-- Пользователь для миграций (CREATE/DROP/ALTER)
CREATE USER app_migrator WITH PASSWORD '<vault>';

-- Пользователь приложения (только DML)
CREATE USER app_user WITH PASSWORD '<vault>';
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app_schema TO app_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA app_schema GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
-- НИКОГДА не подключайте приложение суперпользователем/postgres
```

### 3.5 Безопасность подключения

- **`sslmode=verify-full`** — проверяет сертификат сервера по CA и имени хоста.
  `require` (без проверки CA) уязвим к MITM.
- Аутентификация **scram-sha-256** (`pg_hba.conf`) — md5 устарел.
- `pg_hba.conf` — строгий белый список: только подсеть приложения.

### 3.6 Шифрование

- **При хранении:** у управляемого Postgres TDE включается автоматически. При
  самостоятельном хостинге — LUKS или шифрование на уровне диска, плюс шифрование WAL.
- **При передаче:** TLS обязателен (см. 3.5).
- **На уровне полей** для PII / карт / медицинских данных:
  - Расширение `pgcrypto` — `pgp_sym_encrypt(data, key)` — но ключ должен
    находиться вне Postgres.
  - **Конвертное шифрование**: AES-256-GCM на слое приложения, ключ — из KMS
    (AWS KMS, GCP KMS, Vault Transit).
  - Должен быть описан жизненный цикл ротации ключей (NIST SP 800-57).

### 3.7 pgaudit — обязателен для соответствия

Расширение `pgaudit` логирует DDL, изменения ролей и доступ к чувствительным
таблицам. Это ключевое доказательство для аудитов SOC2 / PCI DSS / HIPAA.

### 3.8 Гигиена резервных копий

- Зашифрованные бэкапы + хранение вне площадки (другая зона доступности, другой облачный аккаунт).
- **Раз в месяц — тест восстановления**: непроверенный бэкап — не бэкап.
- Восстановление на момент времени (архивация WAL) — RPO < 5 мин.
- Ключ шифрования бэкапов должен быть **отдельным** от ключа продакшен-БД.

### 3.9 Пул подключений

`pgx` + **PgBouncer** в режиме transaction pooling. Без ограничения числа
подключений медленные запросы и DDoS сделают базу неотзывчивой.

## 4. Безопасность веб-фронтенда

### 4.1 Эшелонированная защита от XSS

**Три типа:**

- **Отражённый** — из URL сразу в ответ сервера
- **Хранимый** — попадает из базы при рендере (самый опасный)
- **DOM-based** — искажение выполняет сам клиентский JS

**React/Next экранируют автоматически**, но:

1. При использовании `dangerouslySetInnerHTML` обязателен **`DOMPurify`**
   (лучше на стороне сервера).
2. `href={...}` — фильтруйте схему `javascript:`, если URL вводит пользователь.
3. **Trusted Types API** (CSP `require-trusted-types-for 'script'`) — в
   современных браузерах закрывает DOM XSS почти полностью.

### 4.2 CSP (Content Security Policy)

Современная рекомендация — **строгий CSP с nonce и strict-dynamic**:

```ts
// Next.js middleware.ts
const nonce = crypto.randomUUID();
const csp = [
  `default-src 'self'`,
  `script-src 'nonce-${nonce}' 'strict-dynamic'`,
  `style-src 'self' 'unsafe-inline'`,           // если Tailwind и подобное требуют inline — оставить unsafe-inline
  `img-src 'self' data: https:`,
  `font-src 'self' data:`,
  `connect-src 'self' https://api.example.com`,
  `frame-ancestors 'none'`,                     // кликджекинг
  `base-uri 'self'`,                            // XSS через тег base
  `form-action 'self'`,
  `require-trusted-types-for 'script'`,         // DOM XSS
  `upgrade-insecure-requests`,
  `report-uri https://example.report-uri.com/r/d/csp/enforce`,
].join('; ');
```

**`'unsafe-inline'` для скриптов — НИКОГДА.** Для стилей решайте по ситуации с
tailwind и CSS-in-JS. Если inline-стили не используются, уберите `'unsafe-inline'` и там.

### 4.3 CSRF

| Модель аутентификации | Защита от CSRF |
|---|---|
| Bearer-токен (заголовок Authorization) | Не нужна — не передаётся через куки |
| Сессия в куках | **Double-submit cookie** + `SameSite=Lax` (для изменяющих запросов — по возможности `SameSite=Strict`) |
| Смешанная (кука + JWT) | Со стороны куки CSRF-токен обязателен |

```go
// gorilla/csrf — токен пишется в куку и передаётся в заголовке X-CSRF-Token
```

В этом шаблоне используется комбинация сессии в куках и bearer, поэтому защита
обеспечивается заголовком `X-CSRF-Token`.

### 4.4 SSRF (OWASP A10:2021)

Server-Side Request Forgery — сервер выполняет запрос по URL, введённому
пользователем. Атакующий получает доступ к:

- Сервису метаданных AWS (`http://169.254.169.254`) — кража учётных данных
- Внутренней админ-панели (`http://10.0.0.1:8080`)
- Внутренним сервисам на localhost

**Защита:**

- Белый список URL (разрешённые хосты) — идеально
- Блокировка приватных диапазонов IP (RFC 1918, 169.254/16, ::1/128, fc00::/7)
- Проверка фактически разрешённого IP через `Transport.DialContext` HTTP-клиента
- Осторожность с атаками через редирект во внутреннюю сеть

### 4.5 Открытый редирект

```go
// ❌ Опасно
http.Redirect(w, r, r.URL.Query().Get("return_to"), 302)

// ✅ Белый список
allowed := map[string]bool{"/dashboard": true, "/admin": true}
if !allowed[returnTo] { returnTo = "/" }
```

### 4.6 Заголовки изоляции браузера (современные)

| Заголовок | Значение |
|---|---|
| **Cross-Origin-Opener-Policy: same-origin** | Изолирует opener окна (побочный канал Spectre) |
| **Cross-Origin-Embedder-Policy: require-corp** | Нужен для SharedArrayBuffer, изолирует от iframe других источников |
| **Cross-Origin-Resource-Policy: same-site** | Ограничивает встраивание ресурсов |

### 4.7 Заголовки безопасности (на каждом ответе)

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Content-Type-Options: nosniff
X-Frame-Options: DENY                      # перекрывается CSP frame-ancestors, но нужен старым браузерам
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: same-site
```

Настраивайте, пока `securityheaders.com` не покажет A+.

### 4.8 CORS

В этом шаблоне CORS реализован не на Fiber, а на стандартном `net/http`
middleware в стиле chi (`CORSMiddleware()` в `internal/http/middlewares`, вида
`func(http.Handler) http.Handler`). Он проверяет точное совпадение origin с белым
списком и явно перечисляет разрешённые методы и заголовки:

```go
// internal/http/middlewares — CORS в стиле chi (краткий каркас)
func CORSMiddleware() func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            origin := r.Header.Get("Origin")
            if allowedOrigins[origin] { // белый список с точным совпадением
                w.Header().Set("Access-Control-Allow-Origin", origin)
                w.Header().Set("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,PATCH")
                w.Header().Set("Access-Control-Allow-Headers", "Authorization,Content-Type,X-CSRF-Token,X-Tenant-ID")
                w.Header().Set("Access-Control-Allow-Credentials", "true")
                w.Header().Set("Access-Control-Max-Age", "300")
            }
            // По спецификации CORS НИКОГДА не сочетайте Allow-Origin="*" с Allow-Credentials=true
            if r.Method == http.MethodOptions {
                w.WriteHeader(http.StatusNoContent)
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}
```

### 4.9 Загрузка файлов

- Определяйте MIME-тип по содержимому (magic bytes), а не по расширению
- Ограничение размера — на уровне middleware
- **Раздавайте с отдельного домена** — изоляция от кук и от XSS
- Сканируйте ClamAV или облачным антивирусом
- **Полностью перегенерируйте имя файла** (`uuid + расширение`) — защита от
  path traversal и атак с кодировками

### 4.10 Subresource Integrity (SRI)

Если JS/CSS загружается с CDN:

```html
<script src="https://cdn.../jquery.js"
  integrity="sha384-..."
  crossorigin="anonymous"></script>
```

## 5. Безопасность API

**OWASP API Security Top 10 (2023)** — десятка, специфичная для REST API:

| API# | Пункт | Как решается в этом шаблоне |
|---|---|---|
| API1 BOLA | Авторизация на уровне объекта | tenant.Scope + проверка в обработчике |
| API2 Broken Authentication | Слабая аутентификация | Раздел 1 |
| API3 Broken Object Property Level Auth | Mass assignment | Белый список DTO (поля перечислены явно при биндинге) |
| API4 Unrestricted Resource Consumption | DoS | middleware.RateLimiter + middleware.PaginationLimit |
| API5 BFLA | Авторизация на уровне функции | middleware auth.RequirePermission |
| API6 Unrestricted Access to Sensitive Business Flows | Перечисление, боты | CAPTCHA / proof-of-work / поведенческий анализ |
| API7 SSRF | раздел 4.4 |  |
| API8 Security Misconfiguration | Открыто по умолчанию | Усиление инфраструктуры |
| API9 Improper Inventory Management | Теневые API | Обязательная спецификация OpenAPI; конвейер генерации типов |
| API10 Unsafe Consumption of APIs | Сторонние сервисы | Таймауты, валидация схемы |

### 5.1 Mass assignment / over-posting

```go
// ❌ НЕВЕРНО
var u User
c.BodyParser(&u)        // атакующий подставит is_admin=true
db.Save(&u)

// ✅ ВЕРНО
var req struct {
    Email string `json:"email" validate:"required,email"`
    Name  string `json:"name"  validate:"required,max=100"`
}
c.BodyParser(&req)
u.Email = req.Email
u.Name = req.Name
db.Save(&u)
```

### 5.2 Идемпотентность

Поддерживайте заголовок `Idempotency-Key` для POST / PATCH (шаблон Stripe /
Square). В этом шаблоне есть `middleware.IdempotencyKey(redis, 24h)`.

### 5.3 Пагинация и лимиты ресурсов

- `?limit=` максимум 100. `middleware.PaginationLimit(100)` уже подключён.
- Предпочтительна пагинация по курсору (быстрее offset и меньше гонок).
- Ограничение размера тела запроса — middleware net/http (в этом шаблоне
  `BodySizeLimitMiddleware` ограничивает тело 4 МиБ через `http.MaxBytesReader`).
- Таймаут запроса (`middleware.Timeout(5*time.Second)`).

### 5.4 Особенности GraphQL (если используется)

- Ограничение глубины запроса (максимум 10)
- Оценка сложности запроса
- Отключение introspection в продакшене
- Persisted queries

### 5.5 Безопасность webhook

Если вы принимаете webhook от внешнего сервиса:

- **HMAC-подпись** — `X-Signature: hmac_sha256(secret, body)`, сравнение за постоянное время
- **Метка времени** — заголовок `X-Timestamp`, отклонять при расхождении более 5 минут (повтор)
- **Белый список IP** или mTLS

- OWASP API Security Top 10 2023
- OWASP ASVS V13 (API and Web Services)

## 6. Безопасность мобильных приложений

**OWASP MASVS v2** имеет три уровня:

| Уровень MASVS | Цель |
|---|---|
| L1 | Стандартная безопасность (почти любое потребительское приложение) |
| L2 | Эшелонированная защита (банки, здравоохранение) |
| L3 | + Устойчивость к обратной разработке (DRM, банковское ядро) |

**По умолчанию для шаблона: L1+. Для банковских сценариев — L2.**

### 6.1 Хранилище (MASVS-STORAGE)

- **iOS:** Keychain Services API, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`
  + `kSecAttrAccessControlFlags = .biometryCurrentSet`.
- **Android:** EncryptedSharedPreferences (Jetpack Security) либо шифрование через
  Keystore. Запрашивайте **аппаратный StrongBox**
  (`KeyGenParameterSpec.Builder.setIsStrongBoxBacked(true)`, API 28+).
- **React Native:** `react-native-keychain` (под капотом Keychain/Keystore).
- **Flutter:** `flutter_secure_storage`.
- Чувствительные данные не должны попадать в кэш, логи, скриншоты и дерево
  доступности (например, на iOS `UITextField.isSecureTextEntry = true`).

### 6.2 Сеть (MASVS-NETWORK)

- Только TLS 1.2+. Настраивается в ATS (iOS) и Network Security Config (Android).
- **Закрепление сертификата (pinning)** — предпочтительно закреплять публичный
  ключ (тогда ротация сертификата не требует обновления pin):
  - iOS: `URLSessionDelegate.urlSession(_:didReceive:completionHandler:)`
  - Android: `CertificatePinner` (OkHttp) или `network-security-config.xml`
  - **Держите резервный pin** — заранее опубликованный публичный ключ следующего
    сертификата очень пригодится
- mTLS — для банковских и админских сценариев.

### 6.3 Аутентификация (MASVS-AUTH)

- Биометрия — используйте системные API (LocalAuthentication, BiometricPrompt). Не изобретайте своё.
- Хранение токенов — см. раздел 6.1.
- Блокировка приложения — повторная аутентификация после n минут бездействия.

### 6.4 Платформа (MASVS-PLATFORM)

- **Deep links** — используйте Universal Links (iOS) / App Links (Android),
  избегайте собственных схем (другое приложение может зарегистрировать такой же `myapp://`).
- При использовании WebView — `setAllowFileAccess(false)`, и не размещайте
  чувствительный контент в WebView с включённым `setJavaScriptEnabled`.
- IPC — минимизируйте число экспортируемых компонентов.

### 6.5 Код и защита от реверса (MASVS-CODE / RESILIENCE)

- **Никогда** не зашивайте API-ключи в приложение. Их достанут декомпиляцией.
- Чувствительную логику держите на бэкенде.
- **Аттестация приложения:**
  - iOS: `DeviceCheck` + **App Attest** (iOS 14+) — токен аттестации от Apple
  - Android: **Play Integrity API** (устаревший SafetyNet больше не актуален)
- Анти-отладка, защита от подмены (L2+): обнаружение root/jailbreak и отладчика.
  Но не рассчитывайте, что это «не обойдут» — это лишь один слой эшелонированной защиты.
- ProGuard/R8 (Android) — обфускация классов и методов.

### 6.6 Соответствие стандартам

- OWASP MASVS v2
- OWASP MASTG (Mobile Application Security Testing Guide)
- NIST 800-163 (проверка приложений)

## 7. Инфраструктура и облако

### 7.1 TLS

- Только TLS 1.2+. **Предпочтительно TLS 1.3** (прямая секретность, гарантии 0-RTT).
- Настраивайте до оценки **A+** на `ssllabs.com/ssltest`.
- Список предзагрузки HSTS ([hstspreload.org](https://hstspreload.org)).
- Прозрачность сертификатов — Caddy / Let's Encrypt делают это автоматически.

### 7.2 Безопасность DNS и домена

- **Записи CAA** — `example.com. CAA 0 issue "letsencrypt.org"`. Другие CA не
  смогут выпустить сертификат.
- **DNSSEC** — от подмены DNS.
- **Защита от захвата поддоменов:** удаляйте неиспользуемые CNAME (например,
  CNAME указывает на S3-бакет, а сам бакет удалён — атакующий создаёт бакет и
  забирает поддомен).
- Аутентификация почты: **SPF + DKIM + DMARC** (p=reject) — защита от подделки отправителя.

### 7.3 Управление секретами

- **Никогда не кладите в git.** `gitleaks`, `trufflehog` в pre-commit и CI.
- Cloud KMS / Vault / AWS Secrets Manager / GCP Secret Manager.
- Локальная разработка: `.env` + `.gitignore` + `direnv` + 1Password CLI / `op`.
- Политика ротации секретов (NIST 800-57):
  - Пароль БД: ежегодно
  - API-ключ: 90 дней
  - Ключи шифрования: версионирование с самого начала, ротация 90–365 дней

### 7.4 Безопасность контейнеров

- Образы **Distroless / Wolfi / Chainguard** — меньше поверхность атаки.
- Пользователь не root (`USER 65532`).
- Корневая ФС только для чтения (`docker run --read-only` / в K8s
  `securityContext.readOnlyRootFilesystem: true`).
- Сканирование образов **`trivy` + `grype`** в CI.
- **Многоэтапная сборка** — инструменты сборки не остаются в продакшен-образе.

### 7.5 Подписание образов (SLSA / Sigstore)

```bash
cosign sign --key cosign.key myorg/myapp:v1.0
# При загрузке:
cosign verify --key cosign.pub myorg/myapp:v1.0
```

Admission controller в K8s (Sigstore policy-controller) — допускать только подписанные образы.

### 7.6 Усиление Kubernetes

- **Namespace** — изоляция по арендаторам или сервисам.
- **NetworkPolicy** — трафик между подами: по умолчанию запрет + явные разрешения.
- **Pod Security Standards** (профиль Restricted).
- **Секреты:** внедряйте не через env, а через projected volume и смонтированные файлы.
- **Шифрование etcd при хранении** — через KMS.
- **RBAC** — минимальные привилегии, не запускайте сервисы под ClusterAdmin.
- **Политика загрузки образов** — фиксированный digest (`@sha256:...`), а не тег.

### 7.7 Service mesh / mTLS

При большом числе микросервисов — **Istio / Linkerd**:

- Автоматический mTLS
- Политики уровня L7 (метод HTTP, путь)
- Наблюдаемость

### 7.8 Сеть

- **База данных НЕ ДОЛЖНА быть открыта в интернет.** Только внутри VPC.
- **WAF** (Cloudflare, AWS WAF) — набор правил OWASP CRS.
- **DDoS:** прокси Cloudflare, AWS Shield.
- **SSH:** отключите пароли, только ключи, fail2ban. Ещё лучше —
  Identity-Aware Proxy / AWS SSM Session Manager, чтобы SSH вообще не открывать.
- **Zero-trust** (модель BeyondCorp) — не периметр, а проверка устройства и
  личности при каждом обращении сотрудника.

### 7.9 Соответствие стандартам

- CIS Docker / Kubernetes Benchmarks
- NIST SP 800-190 (безопасность контейнеров)
- NIST SP 800-207 (архитектура нулевого доверия)
- CIS Controls v8: 12 (сеть), 4 (безопасная конфигурация), 7 (управление уязвимостями)

## 9. Логи, мониторинг и реагирование на инциденты

### 9.1 Что логировать

**Обязательно (NIST 800-92 / NIST CSF DE.AE):**

- События аутентификации (успех, неудача, блокировка, обход MFA)
- Отказы авторизации (403)
- Действия администраторов (изменение конфигурации, назначение ролей, создание/удаление пользователей)
- Доступ к чувствительным данным (просмотр PII, экспорт)
- Платёжные и финансовые операции
- Аномальный трафик (всплеск 5xx, всплеск ошибок, высокая частота запросов)
- Запуск/остановка приложения, события развёртывания

**Формат:** структурированный (JSON), семантические соглашения OpenTelemetry:

- `service.name`, `service.version`
- `user.id`, `tenant.id`, `request.id`
- `event.name` (например, `auth.login.success`)
- `severity_number`, `severity_text`

```go
import "go.uber.org/zap"
log.Info("auth.login.success",
    zap.String("user.id", userID),
    zap.Int("tenant.id", tenantID),
    zap.String("request.id", reqID),
    zap.String("ip", ip),
)
```

### 9.2 Что не логировать

**НИКОГДА не пишите в логи:**

- Пароли в открытом виде
- Полный номер карты (PAN)
- API-ключи, JWT, токены сессии и refresh
- Ненужные PII (почта, телефон, SSN) — хешируйте или маскируйте
- Медицинские данные (HIPAA)

**Инструменты:** напишите обёртку для `Encoder` в zap, которая скрывает PII-поля.
На стороне бэкенда логов (Loki / Datadog) отфильтруйте повторно.

### 9.3 Целостность логов

- Защита от подделки: WORM-хранилище (AWS S3 Object Lock) или аудит на блокчейне
  (в большинстве случаев избыточно).
- Пересылайте логи на машину вне приложения — тогда их нельзя стереть при
  компрометации хоста.

### 9.4 Мониторинг / SIEM

| Стек | Пример |
|---|---|
| Открытый | Loki + Grafana + Tempo + Mimir |
| SaaS | Datadog, New Relic, Honeycomb |
| Корпоративный SIEM | Splunk, Elastic SIEM, Sentinel, Chronicle |

**Оповещения (NIST CSF DE.AE-5):**

- 100+ неудачных входов за минуту → critical
- Вход администратора с новой геолокации / устройства → high
- Всплеск длительности запросов к БД → medium
- Доля 5xx > 5% → critical

### 9.5 Реагирование на инциденты (NIST SP 800-61r2)

**Шесть фаз:**

1. **Подготовка** — план реагирования, runbook, контакты
2. **Обнаружение и анализ** — маршрутизация оповещений, разбор
3. **Сдерживание** — изоляция, предотвращение распространения
4. **Устранение** — ликвидация первопричины
5. **Восстановление** — возврат сервиса
6. **После инцидента** — разбор, извлечённые уроки

**Шаблон плана реагирования (хватит трёх страниц):**

- График дежурств (PagerDuty / Opsgenie)
- Дерево решений (кто вправе объявлять сдерживание)
- Каналы коммуникации (страница статуса, SLA уведомления клиентов —
  **GDPR: 72 часа**, PCI — 24 часа для банка)
- Шаблон разбора (хронология, первопричина, задачи)
- Настольные учения — ежеквартально, чтобы проверять, например, «как мы обнаружим
  длительное скрытое присутствие атакующего».

### 9.6 Соответствие стандартам

- NIST SP 800-92 (управление логами)
- NIST SP 800-61r2 (обработка инцидентов)
- NIST CSF 2.0 Detect / Respond / Recover
- ISO 27001:2022 A.5.24–A.5.30

## 10. Приватность и соответствие

### 10.1 Приватность по замыслу (GDPR ст. 25)

- **Минимизация данных** — собирайте только необходимое.
- **Ограничение цели** — не используйте данные вне цели сбора.
- **Ограничение хранения** — удаляйте по истечении установленного срока
  (DSR — запрос субъекта данных).
- **Право на забвение** — по запросу пользователя должен работать готовый конвейер.
- **Оценка воздействия на защиту данных (DPIA)** — если новая функция обрабатывает PII.

## 11. Безопасность AI/LLM

Если есть интеграция с LLM. **OWASP Top 10 for LLM Applications (2023)**:

| LLM# | Пункт | В этом шаблоне |
|---|---|---|
| LLM01 Prompt Injection | Пользовательский ввод отменяет системный промпт | Санитизация ввода, разделение каналов сообщений |
| LLM02 Insecure Output Handling | Выполнение HTML/SQL/кода из вывода LLM без проверки | Валидация вывода, песочница |
| LLM03 Training Data Poisoning | Состязательные данные дообучения | Обучение в песочнице, происхождение данных |
| LLM04 Model DoS | Token bomb | Лимиты запросов, бюджет токенов |
| LLM05 Supply Chain | Целостность файлов модели | Sigstore для артефактов модели |
| LLM06 Sensitive Information Disclosure | Модель раскрывает PII в обычном выводе | Дифференциальная приватность, детектор PII как ограничитель |
| LLM07 Insecure Plugin Design | Плагин → произвольный код | Белый список плагинов, песочница |
| LLM08 Excessive Agency | Слишком много прав на выполнение у LLM | Человек в контуре, инструменты с ограниченной областью |
| LLM09 Overreliance | Доверие выводу LLM без проверки | Предупреждения в UX, валидация |
| LLM10 Model Theft | Кража весов | Контроль доступа, водяные знаки |

**В этом шаблоне LLM нет.** Если он появится позже:

- Отправляйте промпт как **структурированный JSON**, а не конкатенацию строк.
- **Изолируйте пользовательский ввод разделителями** (`<user_input>...</user_input>`).
- Вызовы инструментов LLM выполняйте **под отдельной ролью API** — правила
  аутентификации и арендаторов продолжают действовать.

## 13. Криптография

**Золотое правило: «Don't roll your own crypto».** Используйте только стандартные библиотеки.

### 13.1 Рекомендации по алгоритмам (NIST SP 800-131A r2 + OWASP 2024)

| Назначение | ✅ Верно | ❌ Устарело |
|---|---|---|
| Хеширование паролей | Argon2id, bcrypt (cost 10+), scrypt | MD5, SHA-256 напрямую, SHA-1 |
| Симметричное шифрование | **AES-256-GCM**, **ChaCha20-Poly1305** | AES-CBC (padding oracle), DES, 3DES, RC4 |
| Хеш | SHA-256, SHA-3, BLAKE2 | MD5, SHA-1 |
| HMAC | HMAC-SHA-256 |  |
| Асимметричное | **Ed25519** (подпись), **X25519** (обмен ключами), **ECDSA P-256+** | RSA <2048, DSA |
| KDF | HKDF-SHA-256, scrypt | PBKDF1 |
| TLS | TLS 1.3 (по умолчанию), 1.2 как запасной | TLS 1.0/1.1, весь SSL |

### 13.2 Случайность

```go
import "crypto/rand"  // ✅
import "math/rand"    // ❌ НИКОГДА для секретов!
```

Токены / nonce / соль — обязательно `crypto/rand`.

### 13.3 Готовность к постквантовой эпохе

**В августе 2024 года NIST финализировал стандарты PQC:**

- **ML-KEM** (FIPS 203) — инкапсуляция ключей
- **ML-DSA** (FIPS 204) — цифровая подпись
- **SLH-DSA** (FIPS 205) — подпись на основе хешей

**Гибридный TLS** (X25519+Kyber768 у Cloudflare) уже применяется в продакшене.
Составьте план перевода долгоживущих ключей подписи на PQC до 2030 года
(остерегайтесь атак «собрать сейчас, расшифровать позже»).

### 13.4 Жизненный цикл ключей (NIST SP 800-57)

- **Генерация:** внутри HSM или облачного KMS.
- **Распространение:** только по TLS.
- **Хранение:** НИКОГДА в обычных файлах; tmpfs тоже нежелателен (дамп памяти).
- **Ротация:** по расписанию и при инциденте.
- **Уничтожение:** крипто-шреддинг (удаление ключа = данные невосстановимы).

### 13.5 Соответствие стандартам

- NIST FIPS 140-3 (валидация криптографических модулей)
- NIST SP 800-57, 800-131A
- OWASP Cryptographic Storage Cheat Sheet

На каждом этапе «сделано» соответствует конкретным пунктам ASVS:

### Этап 1 — базовый уровень ASVS L1 (любое приложение)

- [ ] HTTPS везде + HSTS preload

## Золотые принципы

1. **Эшелонированная защита** — одного рубежа мало. WAF + валидация в приложении +
   RLS в БД + изоляция арендаторов + журнал аудита — всё вместе.
2. **Минимальные привилегии** — пользователь, сервис, роль БД не должны иметь
   больше прав, чем нужно для работы.
3. **Безопасный отказ** — при ошибке система должна закрываться, а не открываться.
   `default deny`.
4. **Не изобретайте криптографию** — используйте только библиотеки, рекомендованные NIST/IETF.
5. **Логируйте всё важное и ничего чувствительного.** Скрытие PII на этапе приёма.
6. **Сдвиг влево, безопасный релиз** — переносите безопасность в CI, непроверенный
   код наружу не уходит.
7. **Считайте, что вас уже взломали** — проектируйте с позиции «если вас
   скомпрометировали». Насколько ограничено боковое перемещение?
8. **Безопасность — это процесс, а не функция** — не разовая настройка, а
   постоянные ревью и обновления.

---

> **Девиз:** самая безопасная система — та, которой не существует. Но если идти в
> описанном порядке, вы закроете **95%+** риска от тех классов уязвимостей,
> которых в продакшене уже давно можно избежать. Чтобы добраться до оставшихся
> 5%, продолжайте регулярно обновлять модель угроз, проводить пентесты и вести мониторинг.
